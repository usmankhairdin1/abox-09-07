Scope: `tools/figma-plugin` reference layer only. No `src/**` changes, no B1 changes, no B3 work, no token re-interpretation.

## 2. Leading diagnosis for the single failing check

`verifyB2()` compares stored values with exact equality:

```js
if (!v || v.valuesByMode[light] !== f.value || v.valuesByMode[dark] !== f.value) floatOk = false;
```

Every integer-valued variable (600, 500, 11, 10, 0) round-trips exactly. The only three non-integer values are `-2.8`, `-3.2` and `1.02` — values that are not exactly representable in binary floating point and that Figma may return with a minutely different stored representation than the JS literal written. Exact `!==` then fails while the Figma UI, the inventory log and the human-readable report all show identical numbers. That pattern matches the observed symptom precisely: everything else passes, and no value looks wrong.

This remains a diagnosis, not a proven fact, because it can only be confirmed inside real Figma. Step 3 therefore proves it before anything is corrected.

## 3. Proof step before any correction (first implementation action)

Add a temporary, evidence-only diagnostic to the B2 verification output: for each of the 10 FLOAT variables, print the expected value, the raw stored Light value and raw stored Dark value at full precision (`Number.prototype.toPrecision(20)`), plus the absolute difference. Run `B2 Verify` in Figma Desktop.

- If one or more of `-2.8`, `-3.2`, `1.02` shows a non-zero sub-1e-9 difference → precision confirmed, apply section 4.
- If any value differs materially (e.g. a stale value from an older run) → the cause is a stale write, and the correction is instead to re-run `B2 Create`, which already overwrites values for existing variables.
- If any value is `undefined` for a mode → the cause is mode-id resolution, and the correction targets the mode lookup only.

No correction is chosen until this run names the cause.

## 4. Minimal correction (precision case)

In `verifyB2()` only, compare FLOAT values with a tolerance instead of strict identity:

- helper `floatMatches(stored, expected)` → `typeof stored === "number" && Math.abs(stored - expected) <= 1e-9`
- applied to both Light and Dark
- on failure, the check label lists exactly which variable/mode failed and by how much, so a real mismatch can never hide behind the tolerance
- the Light/Dark parity check uses the same tolerance for numbers

Nothing about the approved specification changes: same collection name `ABox/Typography`, same 19 variables, same 9 STRING + 10 FLOAT split, same Light/Dark modes, same derived values, same descriptions, same recorded limitations. Only the verifier's comparison becomes numerically honest.

## 5. Files that would change

- `tools/figma-plugin/README.md` — one paragraph recording the float-tolerance rule and why it is not a relaxation of source fidelity.

Not changed: `src/styles.css` and all of `src/**`; `extract-b2.mjs`; `tokens-b2.js`; every B1 file, collection and variable; B3–B10 code paths; `ABox Proof — Scratch`.

## 6. How B1 stays untouched

The correction touches only code inside `verifyB2()`. `ensureB1Variable`, `ensureB1Collection`, `b1Collections`, `ABOX_B1` and `verifyB1` are not edited. The existing B2 check "B1 still holds 200 variables" and "the nine B1 collections still exist exactly once each" stay in place and must keep passing after the re-run.

## 7. Re-run and proof sequence (real Figma Desktop)

1. `B2 Verify` with the diagnostic — capture the raw-precision evidence identifying the cause.
2. Apply the correction, rebuild `code.js`, reload the plugin.
3. `B2 Create` — expect variables updated, zero created, zero duplicates.
4. `B2 Verify` — expect all checks PASS, including `numeric values match production in both modes`, with the per-variable evidence lines showing each expected/stored pair.
5. `B2 Create` again, then `B2 Verify` again — idempotency: still 19 variables, still PASS.
6. `B1 Verify` — 9 collections, 200 variables, unchanged.
7. Until steps 1–6 are executed in Figma Desktop, the evidence state stays `REAL FIGMA NOT VERIFIED`.

`font-variation-settings` axes, OpenType feature settings, `font-variant-numeric`, `text-transform`, CSS fallback stacks stored verbatim as STRING, Tailwind library-owned defaults, and JetBrains Mono being loaded but unreferenced by `--font-mono`. All stay in `ABOX_B2.limitations` exactly as they are.
